[L0002] A probe that runs a repo's own oracle inherits that oracle's side effects | candidate | added: 2026-08-18 | tags: licensing-provenance, golden-governance | lesson: When any external tool verifies a gate BEHAVIOURALLY, it must invoke the target's real oracle — and that oracle writes state (here `./verify` writes `.harness/last-verify.json` and clears `.harness/dirty`). So the probe's cleanup contract extends past its own artifacts to every file the invoked oracle touches; restoring only what the probe created leaves the repo mutated by a check that was supposed to be read-only. Two consequences for a resident: (1) an unexplained oracle state whose timestamp/hash postdates your own last run, on a clean tree, may be a peer's probe rather than a defect — re-run and compare before hunting; (2) when writing any tool that shells out to another project's oracle, snapshot-and-restore its state files, including the absent case (a repo with no prior record must not gain one). | evidence: 2026-08-18 — a passing `gate-fires` probe left `{"target":"fast","exit":1,"git":"0b60698"}` in this repo's record and tripped the Stop hook; the red represented the peer's check SUCCEEDING. Reported upstream; fixed in kit 2.2.2 (both `_gate_fires` and `_gate_report` now snapshot/restore both state files in the plant's try/finally), and autonomous's regression test was run against the reverted code to prove it failed with that literal record first. Re-verified on this tree at kit 2.2.2: record byte-identical before/after the probe, no `dirty` flag gained, no stray plant. Generalized form also carried as autonomous LIBRARY L0006. | falsifier: if a probe is found that mutates a target's oracle state without restoring it AND that is judged acceptable (e.g. the state is defined as caller-owned), the cleanup-contract claim is wrong — narrow the entry to the diagnostic half. | supersedes: the kit-2.2.1-specific form of this entry (symptom no longer reproduces as of kit 2.2.2; the principle is what survives)
